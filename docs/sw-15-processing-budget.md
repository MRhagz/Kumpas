## Behavior

Approval saves an immutable approved profile and starts its SW-02 run in one database transaction. Run ID, profile version, start and deadline persist before the browser navigates to analysis. Extraction remains outside that run's timer and uses a separate bounded invocation budget. All analysis, retrieval, embedding, synthesis, explanations, automatic delays, report assembly and PDF generation/storage use the original run deadline. `maxDuration = 300` declares the route runtime allowance; it does not give a later report invocation another processing budget.

Each eligible provider operation makes at most two attempts. Default delay is two seconds; longer Retry-After seconds/HTTP dates or Gemini RetryInfo are followed only when they leave time before the deadline. Explicit validation/configuration failures, authentication/permission failures, daily/zero/exhausted quota and deadline exhaustion receive no automatic retry. Unknown application errors fail without a speculative retry. SDK retry attempts are explicitly set to one so hidden retries cannot multiply the policy. Retrying specialist generation does not re-embed or re-query; the dispatcher does not retry a whole specialist. Explanation failure keeps the existing explicit unavailable/degraded fallback; deadline failures stop the run.

The new short, service-role-only invoker RPC serializes stage claims/results on the same session lock as SW-02 approval and publication. Duplicate claims fail. Results are accepted only for the active owner/session/run/profile, expected phase and remaining wall-clock deadline. Analysis outputs reside on that run, rather than replacing unversioned recommendation rows from a late worker. Reports use its immutable profile and saved results. A monotonic reservation counter assigns a unique PDF object version before each report attempt, including failed attempts. This prevents an old upload or cleanup from affecting a newer run; report version gaps are intentional. Private non-overwriting PDF writes precede the atomic SW-02 report publication, which ends the budget. Report requests carry the run token. Reads of a ready draft do not regenerate or restart its clock. SQL and the application consistently reject completion at or after the deadline, preserving SW-02's existing boundary.

A stopped run keeps the approved profile and records the failed stage. Retry is an explicit counselor action, creating a new run and deadline for the same immutable approved version; it cannot silently restart an active run. A killed worker becomes retryable after its recorded deadline. Return opens the existing confirmation session. End Session revokes access before cleanup, removes all PDF versions and deletes profile versions (cascading runs) and report metadata. Cleanup failure remains visible through the existing warnings and retention sweep. Old or cancelled completions cannot restore progress.

## Deployment and scope

Apply `supabase/migrations/20261105081447_sw15_processing_budget.sql` after SW-02 and before deploying the application. It adds phase, failed-stage, recommendations and PDF-reservation fields to `analysis_runs`, a report-generation counter on `sessions`, and two invoker RPCs; existing run/profile/report identity and 300-second/24-hour constraints remain intact. No browser grants or security-definer functions are introduced. Deploy the client, routes, services and migration together. Legacy version-zero sessions must return to confirmation and explicitly approve before starting a timed analysis; the server never infers version-bound approval from their JSON.

No new environment variables or dependencies. Existing Gemini keys, Supabase service credentials and the private `kumpas-reports` bucket remain required. Runtime hosting must support the declared duration; deployment qualification belongs to SW-30. Versioned objects use `{sessionId}/{reportVersion}.pdf`, without overwrite. Cleanup checks publication before deleting an unregistered candidate; an uncertain/late Storage write can leave an inaccessible orphan for the existing retention sweep. Storage abort is best effort; database publication remains authoritative.

The shared deadline requires the basic SW-02 report publication/storage integration here. This does not claim SW-07's corrected input contract, SW-16 scoring, SW-17 partial-evidence handling, SW-19 report content, SW-20's full independent report lifecycle, SW-21's final approval gate, or SW-22/23's full recovery/retention workflows. Existing report release semantics remain pending SW-21; the new draft publication is not counselor approval. No deferred RTM features, student self-entry, college/overseas advising or submission PDFs are added.
